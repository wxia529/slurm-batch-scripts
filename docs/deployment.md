# 部署与更新

执行 `./deploy.sh -h` 或 `./deploy.sh --help` 查看部署用法；帮助模式不会修改部署目录。

## 源码与部署目录

源码仓库保存所有集群的脚本和文档；部署目录只保存当前集群实际使用的文件：

```text
源码仓库：slurm-batch-scripts/
部署目录：~/soft/slurm-batchs/
```

部署时，`deploy.sh` 根据参数从对应集群目录（`mindu/`、`neimeng-2/` 或 `tianjin/`）选择脚本，并从 `docs/clusters/` 选择说明文件。

例如：

```text
docs/clusters/mindu/gaussian.md
→ ~/soft/slurm-batchs/gaussian/README.md

mindu/gaussian/myg16.sh
→ ~/soft/slurm-batchs/gaussian/myg16.sh
```

## 安全边界

部署脚本不会：

- 删除安装目录里已有的文件或目录
- 清空部署目录
- 修改 `Batch.log`
- 修改计算输入和输出文件
- 修改 `.bashrc`、`.bash_profile` 等用户配置
- 覆盖尚未登记的同名文件
- 创建或覆盖 `~/bin` 中的命令
- 把 `/`、当前用户家目录、`/tmp`、`/usr` 等目录当作安装位置
- 穿过符号链接修改安装目录外面的文件

部署脚本使用两份元数据：

```text
~/soft/slurm-batchs/.slurm-batchs-managed
~/soft/slurm-batchs/.slurm-batchs-baseline
```

`.slurm-batchs-managed` 记录当前集群和本项目登记过的相对路径。`.slurm-batchs-baseline` 记录安装根目录、子目录和这些文件的类型、权限与 SHA-256。基线文件自身不写入内容摘要，因为摘要不能放进被摘要的文件里。内容校验只跳过安装根目录上的这一个文件名；该文件仍必须是权限 `444` 的普通文件。隐藏目录和其他路径都会检查。

同一账号可以 `chmod` 后改基线。基线用来发现误写入和意外缺失，不能防止同一账号改写基线后再通过检查。

如果目标目录已经部署另一套集群，部署会在修改权限或文件前停止。暂存和失败恢复使用安装目录之外的临时目录，成功、失败或中止后都会删掉这些临时目录。

## 部署后的目录权限

成功部署结束后，安装目录会收成只读：

| 对象 | 权限 | 含义 |
| --- | --- | --- |
| 目录 | `555` | 可以进入和列出，不能在里面新建、改名或删除 |
| 可执行脚本（`*.sh`，含 `env.sh`） | `555` | 可以读取和执行，不能直接改内容 |
| 其他普通文件 | `444` | 可以读取说明、清单和基线，不能直接改内容 |

属主仍可以对自己的文件执行 `chmod`。这层权限用来减少误写，不使用 `chattr`，也不需要管理员权限。需要手工处理文件时，先对相应目录和文件 `chmod u+w`，处理完后把目录和 `*.sh` 恢复为 `555`，把其他文件恢复为 `444`。

## 下次部署前的检查

已经有基线时，`./deploy.sh <集群>` 会先对照基线，然后才恢复写权限或覆盖文件。以下情况都会列出相对路径并退出，安装目录保持原样：

- 新增路径，包括隐藏文件、隐藏目录和子目录中的文件
- 已记录文件的内容变化
- 已记录路径的权限变化
- 基线中有、目录里已经没有的路径
- 符号链接，以及普通文件、目录以外的对象

`--accept-existing` 不能跳过已经建立的基线。发现差异后，部署不会删除、覆盖或自动改回这些路径。

## 已有安装如何建立基线

新建的空目录可以直接安装：

```bash
./deploy.sh mindu
```

目录里已经有文件、但还没有 `.slurm-batchs-baseline` 时，部署会先打印两类路径：清单已经登记的路径，以及登记之外的路径。此时不会修改目录。确认登记之外没有任何需要保留的路径后，执行一次：

```bash
./deploy.sh --accept-existing mindu
```

这条命令会更新清单里已经登记的文件，写入第一份基线，再把安装目录收成只读。它不会删除列出的额外路径。额外路径还在时，即使加上 `--accept-existing` 也会退出。请先把笔记、日志、隐藏文件和旧的 `.slurm-batchs-stage.*` 暂存目录移出安装目录。

没有 `.slurm-batchs-managed` 的非空目录不能接管。请改用一个空目录安装。

旧版清单没有 `cluster=` 记录时，先确认目录确实属于该集群，再同时给出两个参数：

```bash
./deploy.sh --adopt-legacy --accept-existing mindu
```

之后的更新回到 `./deploy.sh mindu`。同一安装目录仍然不能直接切换集群。

## 检查停下之后

按命令列出的路径处理，再重新执行原来的部署命令：

1. 新增路径：把文件或目录移到安装目录外面。需要删除目录项时，先 `chmod u+w` 它所在的目录。
2. 内容变化：把要保留的副本存到安装目录外面，再从上一版发布包恢复安装目录里的原字节，使 SHA-256 与基线一致。
3. 缺失路径：从上一版发布包把该文件放回原来的相对路径。发布包里的集群说明在 `docs/clusters/<集群>/`，部署后的软件说明是对应的 `README.md`。
4. 权限变化：目录和 `*.sh` 恢复为 `555`，其他文件恢复为 `444`。
5. 符号链接：移出安装目录。部署不会顺着链接修改链接外面的文件。

若基线文件本身损坏，而你已经确认目录里没有未登记文件，可以先把损坏的基线移出目录，再执行 `--accept-existing`。这会用当前源码更新清单中的已有文件并重新记录基线。部署没有提供清空旧目录的默认动作。

更新过程若在重新锁定前失败，会尽量从临时备份恢复刚才的文件内容和权限。请查看命令输出。进程若被强行终止，临时备份可能来不及恢复，需要按上面的清单人工核对。

## 运行时文件写在哪里

安装目录只读之后，提交脚本仍然不需要往安装树里写日志、缓存或临时文件：

- `*-tmp` 写在运行命令时的当前目录，便于之后用 `sbatch` 重提
- `Batch.log` 写在任务目录
- Gaussian 临时文件写在 `$HOME/tmp` 或 `/tmp`

请在计算目录中运行 `myg16.sh` 等命令，并把输入文件放在计算目录。当前目录或输入文件若位于只读安装树内，创建 `*-tmp` 或 `Batch.log` 会失败，已安装的脚本保持不变。`source ~/soft/slurm-batchs/env.sh` 只读取安装目录。

## 部署内容

所有集群都会部署：

- 集群级 `README.md`
- `env.sh`
- 软件提交脚本
- 软件目录中的 `README.md`

部署脚本会自动发现所选集群目录中的软件及其 Shell 脚本，因此各集群的软件集合可以不同。以后新增软件目录时，不需要在部署逻辑中登记特定软件名称。同一部署目录不允许直接切换集群，部署过程也不会删除目标目录中的其他文件。

旧版管理清单没有集群记录时，部署脚本不会根据某个软件名称猜测集群。接管步骤见上文「已有安装如何建立基线」。

## 更新部署

进入源码仓库并获取最新版本：

```bash
cd slurm-batch-scripts
git pull --ff-only
```

随后重新部署当前集群：

```bash
./deploy.sh mindu
# 或
./deploy.sh neimeng-2
# 或
./deploy.sh tianjin
```

安装目录与上次成功部署的基线一致时，重复部署会更新项目文件，并在结束后保持只读。基线不一致时，部署列出路径后停止。第一次把本机制用到旧安装目录时，先按「已有安装如何建立基线」核对；没有基线的旧目录使用 `--accept-existing`，旧清单还没有集群记录时同时加上 `--adopt-legacy`。用户需要重新部署后，只读权限和基线才会生效。

## 发布源码包

项目使用日期 tag 发布完整源码包。发布前先确保目标提交已经推送到 `main`，然后创建并推送一个带注释的 tag：

```text
release-YYYY-MM-DD
```

例如：

```text
release-2026-08-02
```

实际操作示例：

```bash
git switch main
git pull --ff-only
git tag -a release-2026-08-02 -m "Release 2026-08-02"
git push origin release-2026-08-02
```

推送 tag 后，`.github/workflows/release-package.yml` 会自动运行。它依次执行 Shell 语法检查、三个集群的隔离部署测试、只读安装与基线回归测试，以及严格文档构建；任一步失败都不会发布 Release。本次功能交付只修改仓库并打开 Pull Request，不创建 `release-YYYY-MM-DD` 标签，也不在集群上执行部署。

成功后会生成：

```text
slurm-batchs-2026-08-02.tar.gz
```

压缩包来自该 tag 对应提交的全部 Git 跟踪文件，不包含 `.git` 目录，也不包含 `site/` 等被 `.gitignore` 忽略的构建产物。

压缩包会同时：

- 上传到该次 Actions 运行的 Artifact（保留 90 天）
- 附加到同名 GitHub Release 的 Assets

日常下载应使用 GitHub Release 的 Assets；Artifact 主要用于检查某次 Action 运行的构建结果。同一天需要重复发布时，可使用 `release-YYYY-MM-DD-N`，例如 `release-2026-08-02-2`，对应的包名也会带上 `-2`。

如果 Release 没有出现，先到仓库的 **Actions → Build release package** 查看失败步骤；常见原因是 tag 格式不符合要求、文档严格构建失败或部署隔离测试失败。
